# SPEC — 당일 확정(Same-Day Confirmation) 설계안

> **상태: 미구현 (Unimplemented).**
> 이 문서는 설계 기록이다. `collectors/krx.py` 에 해당 코드는 **없다.**
> 운영 v4.1 의 확정 규칙은 `next_day` 단일 경로뿐이다.
>
> 배치: `docs/spec_same_day_confirmation.md` (production 코드 경로 밖)
> 작성: 2026-08-14 · CIO 판정으로 production 에서 제외됨

---

## 0. 왜 문서로만 남기는가

CIO 판정 (2026-08-14):

> 지금 Atlas 가 계속 잡아내는 문제가 '코드는 있는데 실제로 안 도는 경로'인데,
> 굳이 또 그런 경로를 production 코드에 넣을 이유가 없습니다.

맞다. 운영 정본 §13(Execution Evidence Audit)의 취지는 **"완성된 코드도 배선되지 않으면 존재하지 않는 것과 같다"** 인데, 그 원칙을 세워 놓고 스스로 미배선 분기를 새로 만드는 것은 자기모순이다. 이 문서는 나중에 실제로 필요해졌을 때 **설계를 다시 하지 않기 위한 기록**이지, 곧 켤 기능의 예고가 아니다.

---

## 1. 이 기능이 풀려는 문제

운영 v4.1 에서 당일 행은 항상 미확정이다. 따라서 **장 마감 후(15:30 이후) 수동 실행으로 당일 확정 종가를 얻는 경로가 없다.** 다음 항목들이 다음 날 아침까지 밀린다.

- 효성중공업 확정 종가
- SK하이닉스 확정 종가 대비 SMA20 위치
- HD현대중공업 확정 종가
- 당일 기관 수급 확정치

현재 판단: **밀려도 된다.** 판정 재현성과 맞바꿀 만한 가치가 아니다. 이 문서가 필요해지는 시점은 "장 마감 당일에 판정해야만 하는 의사결정"이 실제로 생겼을 때이며, 그때까지는 열지 않는다.

---

## 2. 왜 시각 기준은 안 되는가

1차 초안은 `16:00 KST 이후 + 수급 행 존재 = 확정` 이었고 CIO 가 반려했다.

> pykrx 응답에는 최종성(finality) 플래그가 없다. "수급 행이 존재한다"는 **데이터가 왔다**는 사실일 뿐, 그 값이 더 이상 움직이지 않는다는 보장이 아니다.

**일반 원칙으로 승격한다 (운영 정본 §20-2-1):**

> 원천이 최종성을 알려주지 않으면, 수집기는 최종성을 선언하지 않는다.
> 시각·건수·존재 여부는 최종성의 **필요조건**은 될 수 있어도 **충분조건**이 될 수 없다.
> 충분조건으로 쓰는 순간 그것은 추정치이며, Atlas 는 추정치를 만들지 않는다.

---

## 3. 설계안 — 안정성 게이트 (stability)

확정 근거를 시각이 아니라 **"같은 값이 반복 조회에서 움직이지 않는다"는 관측**으로 둔다.

```python
STABILITY = {
    "window_opens_kst": "16:00",   # 창을 여는 필요조건일 뿐 — 이것만으로는 확정되지 않는다
    "checks": 2,                   # 최초 1회 + 재조회 1회
    "interval_sec": 60,
    "fields": ["open", "high", "low", "close", "volume", "net_value", "net_volume"],
}
```

판정 순서 — **어느 단계에서 멈추든 결과는 '확정하지 않는다'** 이다.

| 단계 | 조건 | 미충족 시 사유 코드 |
| --- | --- | --- |
| 1 | 현재 시각 ≥ `window_opens_kst` | `stability_window_not_open` |
| 2 | 판정용 수급 행(`net_value`·`net_volume`)이 존재 | `investor_rows_absent` |
| 3 | `interval_sec` 뒤 재조회해 `fields` 전부 동일 | `stability_mismatch` |
| 4 | 위 전부 충족 | → `stability_confirmed` |
| — | 모르는 mode | `unknown_policy_mode` |

`stability_mismatch` 일 때는 **무엇이 어떤 값에서 어떤 값으로 움직였는지 원문을 보존**한다. 확정 실패 자체가 관측 자료다.

```json
{
  "reason": "stability_mismatch",
  "evidence": {
    "samples": 2,
    "drift": { "close": [2000, 2100],
               "net_value": [{"기관합계": 0}, {"기관합계": 7}] }
  }
}
```

`detail` 수급(`net_value_detail` 등)은 참고용이므로 비교 대상에서 제외한다. 판정에 쓰지 않는 값의 흔들림 때문에 확정이 막히면 안 된다.

## 4. 검증된 것 / 검증되지 않은 것

이 설계는 2026-08-14 에 스텁 기반으로 한 번 구현·통과한 이력이 있다 (당시 T8-4~T8-8, 6건 PASS). 그때 확인된 것:

- 창 시각 전에는 확정하지 않는다
- 재조회 값이 동일하면 확정한다 (표본 수 기록)
- **종가가 움직이면** 창이 열려 있어도 확정하지 않는다
- **수급만 움직여도** 확정하지 않는다 (늦게 정산되는 쪽이 수급이다)
- 수급 행 자체가 없으면 비교 전에 멈춘다

**검증되지 않은 것 — 이쪽이 훨씬 중요하다:**

- 실제 pykrx 응답이 마감 후 몇 분에, 몇 번에 걸쳐 움직이는지 **모른다.** `checks=2` · `interval_sec=60` 은 근거 있는 값이 아니라 임의값이다.
- 따라서 "60초 간격 2회 동일"이 최종성을 뜻하는지 **알 수 없다.** 두 번 다 같은 잠정치일 수 있다.
- 이 값들을 정하려면 **선행 관측이 필요하다** — 마감 후 일정 시간 동안 반복 조회해 값이 언제 안정되는지를 실제로 며칠 측정해야 한다. 그 관측 없이 켜면, 시각 기준을 안정성 기준으로 이름만 바꾼 것에 지나지 않는다.

---

## 5. 켜기로 결정한다면 — 선행 조건

1. **관측 먼저.** `lab.yml` 에서 마감 후 반복 조회 로그를 최소 5거래일 수집해, 값이 언제 안정되는지 측정한다. (production 수집기를 건드리지 않는다)
2. 그 데이터로 `window_opens_kst` · `checks` · `interval_sec` 를 **근거 있게** 정한다.
3. 그때 v4.2 로 올리고, 회귀 테스트를 함께 넣는다.
4. 켠 뒤에는 **실행 증거**를 남긴다 — 며칠간 `stability_confirmed` / `stability_mismatch` 분포를 보고, mismatch 가 관측되지 않으면 그 게이트는 아무것도 막고 있지 않은 것이므로 다시 의심한다.

---

## 6. 이 문서를 폐기해도 되는 조건

당일 확정이 필요한 의사결정이 6개월간 한 번도 발생하지 않으면 이 문서를 지운다. 쓰이지 않는 설계 문서도 재고이며, 재고는 나중에 "이미 결정된 것"처럼 읽힌다.
